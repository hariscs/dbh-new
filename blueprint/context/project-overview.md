# District Behavioral Health Website - Project Overview

> Headless WordPress frontend in Next.js 16 for districtbehavioralhealth.com:
> WordPress stays the content backend, this app renders it fast and SEO-strong.

Generated by `/overview` from `blueprint/project-plan.md` and
`blueprint/build-plan.md`. Re-run `/overview` after plan changes; don't
hand-edit.

## Problem

The marketing site needs to be fast and crawlable at scale (~600 WordPress
pages) while the content team keeps editing in WordPress. This app decouples the
two: WordPress on the `cms.` subdomain owns content and URL structure, and this
Next.js frontend serves the apex domain with static generation and ISR.

## Users

- **Prospective clients and families** - researching mental health and addiction
  treatment via organic search and paid traffic; need fast, trustworthy pages
  and easy ways to call or submit a form.
- **Referring professionals** - checking facilities, locations, and credibility
  pages.
- **Internal marketing/content team** - edit in WordPress and expect changes
  live within about a minute (ISR or revalidate webhook).

No auth, no signed-in tiers; everything is public.

## Working mode

The site is live and feature-complete. Most ongoing work is small ad-hoc
maintenance (content updates, page tweaks, image swaps) run through `/fix`. The
build-plan roadmap holds only the occasional larger efforts.

## Features

Shipped (build-plan 1-11):

1. **Builder API rendering core** - `fetchPageData` client in
   `src/lib/wordpress.ts`, template components, SEO metadata from the API.
2. **Core marketing pages** - home, contact-us, difference pages, meet the team,
   our-facilities, newsroom, reviews, review-us, privacy-policy, thank-you,
   alumni-rehab-program, rehab-admission (hardcoded components).
3. **Location-served system** - state/city/substance templates under
   `/location-served`, driven by WordPress content.
4. **Root catch-all route** - parentless WordPress pages (incl. custom post
   types) resolve at their own slug with static params, ISR, and real 404s.
5. **Blogs and authors** - listing/pagination and author detail pages.
6. **Facility detail pages** - `/facility` templates.
7. **Quiz** - interactive assessment quiz.
8. **PPC landing pages** - `/ppc` variants for paid traffic.
9. **ISR + revalidation webhook** - 60s revalidate plus secret-protected
   `POST /api/revalidate`.
10. **Third-party integrations** - CallTrackingMetrics number swapping, Jotform
    embeds, TrustIndex reviews widget, gallery/marquee interactions.
11. **Staging deploy pipeline** - GitHub Actions standalone build deployed to
    EC2 with pm2.

Roadmap (occasional larger efforts):

12. **Additional WP-driven pages/templates** - new location, condition, or PPC
    pages as content needs arise.
13. **Performance and SEO pass** - Core Web Vitals, caching, metadata,
    structured data.
14. **Deploy and infra improvements** - production pipeline hardening, automatic

## Data model

This app is stateless: no database, no auth, no stored user data. The "data
model" is the WordPress API contract consumed at build/revalidation time.

### BuilderPageData (`builder/v1/page-data?path=...`)

- `apiVersion` (string)
- `template` (string) - selects the template component to render
- `templateVersion` (number | null)
- `slug` (string)
- `fields` (Record<string, string>) - the page's content fields
- `seo` (`title`, `description`, `canonical`, `robots`) - drives `generateMetadata`
- `meta` (`slug`, `parent`, `updatedAt`, `createdAt`)

### Other WordPress endpoints

- `wp/v2/pages`, `wp/v2/posts` etc. - slugs/links for `generateStaticParams`,
  blog listings, authors
- RRIL interlinking plugin - `[{ link, title }]` cards per page path; `null`
  fallback to hardcoded cards

> These shapes are locked by the WordPress plugins; changes must be coordinated
> with the backend.

## Tech stack

- **Next.js 16** - App Router, `output: 'standalone'`, SSG + ISR
- **React 19 + TypeScript (strict)** - server components by default
- **pnpm** - package manager
- **Plain CSS** - Elementor-derived stylesheets scoped by Elementor page id; no
  Tailwind; Swiper for carousels
- **Headless WordPress (Cloudways)** - content backend at the `cms.` subdomain
- **GitHub Actions + EC2 + pm2** - CI builds the standalone artifact, ships it
  to `/var/www/dbh`

## Monetization

Lead generation for treatment services: tracked calls (CallTrackingMetrics),
Jotform submissions, admissions inquiries. No direct revenue features.

## UI/UX

Replicates the original Elementor/WordPress site, and pixel-perfect parity is a
hard requirement: new pages and edits must match the original exactly (work from
reference images or the live original), no new design system. Main routes:

- `/` - home
- `/location-served/...` - the SEO page system (states, cities, substances)
- `/blogs`, `/authors/...` - blog content
- `/facility/...`, `/our-facilities`, `/our_locations/...` - facilities
- `/ppc/...` - paid landing pages
- `/quiz`, `/contact-us`, `/rehab-admission`, `/reviews`, `/meet-the-team` - conversion and trust pages
- `/[...slug]` - catch-all for parentless WordPress pages

## Deployment

- **Staging (automatic)** - push to `main` triggers
  `.github/workflows/deploy-staging.yml`: pnpm build on the runner (Node 24),
  standalone artifact to EC2 `/var/www/dbh`, pm2 restart, port 3001, health
  check `GET /`, 2 releases kept.
- **Production** - apex domain serves this app from EC2; WordPress backend at
  the `cms.` subdomain on Cloudways.
- **Env vars** - `WORDPRESS_URL` (required), `WORDPRESS_REVALIDATE_SECONDS`,
  `REVALIDATE_SECRET`, `WORDPRESS_SITE_NAME`,
  `WORDPRESS_INTERLINKING_TIMEOUT_MS`.
- **Constraints** - never build on the server; the artifact must stay
  self-contained. No test or typecheck command exists yet, so the only automated
  gates are lint and the build.
