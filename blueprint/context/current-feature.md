# Feature: Sitemap and robots.txt

**From build-plan:** feature 13a
**Status:** not started

## Goal

Give the ~600-page site the two crawl-infrastructure files it is missing in
production: `/sitemap.xml` (currently 404) and `/robots.txt` (currently serves
the HTML 404 page). Both are generated by Next.js route handlers so the sitemap
stays in sync with WordPress content through ISR, with no manual upkeep.

## In scope

- `fetchAllPageLinks()` helper in `src/lib/wordpress.ts` that pages through
  `wp/v2/pages` (per_page=100, `_fields=link,modified`) and returns
  `{ path, updatedAt }[]`, or `null` on failure like the other fetchers.
- `src/app/sitemap.ts` - all published WordPress page URLs as absolute apex
  domain URLs with `lastModified`, plus any app route that exists only in code
  (verified against the route directories), minus exclusions below.
- `src/app/robots.ts` - allow all, `Disallow: /api/` and `/thank-you`, and the
  `Sitemap:` pointer.
- A shared `SITE_URL` constant (env-overridable, default
  `https://districtbehavioralhealth.com`) used by both files. Load-bearing:
  13b's `metadataBase` will reuse it.
- Exclusions from the sitemap: `/thank-you` (conversion page) and `/ppc/*`
  (paid landing pages, no organic discovery wanted). **Confirm the /ppc call
  during review.**

## Out of scope

- Open Graph / Twitter metadata and `metadataBase` wiring (13b).
- JSON-LD structured data (13c).
- Any performance or caching work (13d).
- Per-page noindex detection via the Builder API (would need one request per
  page; the WP `seo.robots` field already handles indexing at the page level).
- Image/news sitemap extensions, sitemap index splitting (only needed past
  50k URLs; the site is ~600).

## Build loop

Build one step at a time, never the whole feature at once.

1. Plan mode lays out the step before any code.
2. The AI implements just that step.
3. It shows the diff (not full files); you read it and understand it.
4. You approve, then choose whether to commit a checkpoint or roll straight on.
   Checkpoints are optional; `/complete` makes the real feature-level commit at the end.

Never accept a step you haven't read. If a diff is too big to review, the step was too big, so split it.

## Data / contracts

- `SITE_URL: string` - exported constant, `process.env.SITE_URL ??
  "https://districtbehavioralhealth.com"`. Load-bearing for 13b
  (`metadataBase`) and 13c (JSON-LD `url` fields).
- `fetchAllPageLinks(): Promise<Array<{ path: string; updatedAt: string }> |
  null>` - `path` is site-relative (`/location-served/usa/ca/...`),
  `updatedAt` is the WP `modified` value. Load-bearing only within 13a.
- WP contract consumed: `wp/v2/pages?_fields=link,modified` with
  `X-WP-Total`-style pagination, same endpoint the `[...slug]` catch-all
  already pages through.

## Testing

- No test runner is configured; verification is dev-server evidence (curl the
  two routes, inspect the XML/text) plus `pnpm lint` and `pnpm build`, per the
  Testing gate in `coding-standards.md`.
- If `/tests` lands before this feature, `fetchAllPageLinks`'s
  pagination/normalization would be the in-scope logic to test.

## Notes for the AI

- Server-only code; nothing here needs `'use client'`.
- Follow the fetcher pattern in `src/lib/wordpress.ts`: return `null` on
  failure, never throw into a route; bounded timeouts; reuse `toRelative`.
- The sitemap route runs at request time under ISR, so a WP outage must
  degrade (code-only routes) rather than 500.
- Custom post types (`facility`, `our_locations`) may not appear in
  `wp/v2/pages`; during Step 2, diff the inventory against the route
  directories and add whatever WordPress doesn't report. Do not silently
  assume `wp/v2/pages` covers everything.
- No em dashes in any generated content, comments only where the code can't
  say it (see coding standards).
