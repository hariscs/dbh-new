# Project Plan

> Generated by `/adopt` from the existing codebase and an interview. Review and
> correct anything marked `> TODO (confirm)`, then run `/overview`.

## 1. Problem - What problem are we solving?

District Behavioral Health needs a fast, SEO-strong public website whose content
teams can edit in WordPress without touching code. This app is the headless
Next.js frontend: WordPress (at the `cms.` subdomain) stays the content backend,
and this site renders it with static generation and ISR so pages are fast and
crawlable at scale (roughly 600 WordPress pages).

## 2. Users - Who is this for?

- Prospective clients and their families researching mental health and addiction
  treatment (organic search and paid traffic).
- Referring professionals checking facilities, locations, and credibility pages.
- Internal marketing/content team, who edit pages in WordPress and expect changes
  live within about a minute.

## 3. Features - What does the MVP need?

Already shipped (see `build-plan.md` for the checklist):

- Core marketing pages (home, contact, difference pages, meet the team, reviews,
  facilities, newsroom, privacy policy, thank-you, quiz)
- Location-served page system: dozens of state/city/substance templates driven by
  the WordPress Builder API
- Root catch-all route so parentless WordPress pages resolve at their own slug
- Blogs, authors, and facility detail pages from WordPress content
- PPC landing pages
- ISR (60s) plus an on-demand revalidation webhook
- CallTrackingMetrics phone-number swapping, Jotform embeds, TrustIndex widget

Next up: more WP-driven pages/templates, performance/SEO work, deploy/infra
improvements.

## 4. Data - What are we storing?

Nothing is stored by this app. It is stateless: all content lives in WordPress
and is fetched at build/revalidation time via `wp-json` endpoints (custom
`builder/v1/page-data`, core `wp/v2`, and the RRIL interlinking plugin). No
database, no auth, no user data.

## 5. Tech - What stack are we using?

- Next.js 16 (App Router, `output: 'standalone'`), React 19, TypeScript (strict)
- pnpm (workspace file present, single app)
- Plain CSS files scoped by Elementor page id (no Tailwind); Swiper for carousels
- Headless WordPress on Cloudways as the content backend
- GitHub Actions builds the standalone artifact and deploys it to an EC2 host
  behind pm2

## 6. Monetize - How will this make money?

Lead generation for treatment services: calls (tracked via CallTrackingMetrics),
form submissions (Jotform), and admissions inquiries. The site itself has no
direct revenue features.

## 7. UI/UX - How should this look and feel?

The design replicates the original Elementor/WordPress site: pages carry over
Elementor markup and per-page-id scoped stylesheets. Visual changes should match
the existing look, not introduce a new design system.

## 8. Deployment - Where and how will this ship?

- App type: Next.js standalone server (SSG + ISR), Node 24, port 3001 behind the
  host's proxy
- Build: `pnpm build` on the GitHub Actions runner (never on the server); the
  self-contained `.next/standalone` artifact is shipped to `/var/www/dbh` on EC2,
  managed by pm2 (`deploy/ecosystem.config.cjs`), keeping 2 releases
- Env vars: `WORDPRESS_URL`, `WORDPRESS_REVALIDATE_SECONDS`, `REVALIDATE_SECRET`,
  optional `WORDPRESS_SITE_NAME`, `WORDPRESS_INTERLINKING_TIMEOUT_MS`
- Health check: `GET /` on the app port
- Domains: apex domain serves this app from EC2; WordPress backend lives at the
  `cms.` subdomain
